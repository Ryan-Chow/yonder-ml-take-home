## What this means for the OrangePi / RKNN target

The rover runs YOLO on the Rockchip NPU via RKNN, which this Mac can't run. Absolute latencies above are therefore not the deployment numbers; the *relative* costs and accuracy deltas are what transfer.

- **Export is lossless.** ONNX FP32 reproduces PyTorch mAP exactly (0.872 vs 0.872); raw outputs differ by ~1e-3 px. ONNX is what `rknn-toolkit2` converts from.
- **INT8 works only if the detection head's decode stays in float.** Quantising every node gives mAP 0.000: the Detect head concatenates box coordinates (0-512 px) and class scores (0-1) into one tensor, and a single INT8 scale can't represent both. Keeping the decode in FP32 (convs still INT8) costs only 0.003 mAP50 / 0.003 mAP50-95 and shrinks the file 3.6x. The same issue applies to RKNN INT8. To my knowledge Rockchip's own YOLOv8 export (rknn_model_zoo) ends the graph before the box decode and runs it on the CPU for this reason; confirm that against the toolkit version the team uses (not verified here). On Apple-silicon CPU the INT8 speed-up is small, but NPUs are built for INT8, so the gain there should be much larger (untested).
- **Input size is the biggest lever.** 320 instead of 512 cuts compute 2.6x and ONNX CPU latency 2.6x, but costs 0.041 mAP50, mostly on bottles (0.054); mallet AP50 drops 0.028. This model was trained at 512; training at 320 would probably recover part of the gap (untested).
- **What I would trade on the rover** (judgement, not measured). The mallet is the priority target and is already at 0.97 AP50. Keep YOLOv8n (with 999 training images a larger model is more likely to overfit than to help, and it costs NPU time), quantise to INT8 with the decode on CPU, and pick the input size from the *required detection distance*: small objects are where this model already struggles (results/hard_examples.md), and downscaling makes distant objects smaller still. A practical pattern: run at 320 for search, switch to 512 (or crop around the last detection) once a candidate appears.
- **Preprocessing cost (measured, CPU):** stretch + CLAHE takes 0.61 ms per 512x512 image and 4.1 ms per 1920x1080 frame (mostly the resize). On the OrangePi this runs on the CPU and can overlap with NPU inference of the previous frame.
- **Not measured:** NMS cost, true NPU latency and power.
